Шаг 1. Создание заказа в API и поиск в БД

В Swagger (https://eddytester.com/lab-api) нажимаем кнопку «Authorize 🔓» справа вверху и вводим свой ключ (например, student_kate). Затем делаем POST /api/orders с промокодом VIPGIFT.

Затем находим свой заказ в DBeaver под своим логином:

SELECT id, client_name, restaurant_id, status, subtotal, total_amount, created_at
FROM orders
WHERE client_name = 'ТвоёИмя';

🔍 Что наблюдаем: в колонке total_amount вернулся NULL, хотя subtotal = 690 ₽.

Шаг 2. Расследование промокода (Ловушка NULL)

Ищем промокод VIPGIFT через нечувствительный к регистру фильтр ILIKE:

SELECT id, code, discount_rub, min_order_rub, is_active
FROM promocodes
WHERE code ILIKE '%gift%';
Главное правило SQL

NULL — это не 0! Любая математическая операция с NULL возвращает NULL:
690 - NULL = NULL. Из-за этого расчёт суммы заказа сломался.

Как спасти запрос с помощью COALESCE:

SELECT o.id, o.client_name, o.subtotal,
       COALESCE(p.discount_rub, 0) AS safe_discount,
       o.subtotal - COALESCE(p.discount_rub, 0) AS calculated_total
FROM orders o
LEFT JOIN promocodes p ON o.promocode_id = p.id
WHERE o.client_name = 'ТвоёИмя';

Шаг 3. Расследование двойного списания (JOIN)

Клиент по заказу #1005 жалуется на удвоенное списание (1 290 ₽ ➔ 2 580 ₽). Соединяем заказ с платежами:

SELECT o.id AS order_id, o.client_name, o.total_amount,
       p.id AS payment_id, p.amount AS paid_amount, p.status, p.transaction_id
FROM orders o
JOIN payments p ON p.order_id = o.id
WHERE o.id = 1005;

🔍 Что наблюдаем: запрос вернул 2 строки! На один заказ создалось 2 платежа со статусом success.

Шаг 4. Детекция всех дублей на проде (GROUP BY + HAVING)

Ищем все заказы, по которым произошло больше одного списания денег:

SELECT order_id, 
       count(*) AS payments_count, 
       sum(amount) AS total_paid
FROM payments
WHERE status = 'success'
GROUP BY order_id
HAVING count(*) > 1;

💡 Шпора для собеса: WHERE фильтрует строки ДО группировки, а HAVING фильтрует группы ПОСЛЕ агрегации.

Шаг 5. Заказ в несуществующий ресторан (LEFT JOIN & DDL)

Ищем заказы, привязанные к несуществующим ресторанам:

SELECT o.id, o.client_name, o.restaurant_id, r.name AS restaurant_name
FROM orders o
LEFT JOIN restaurants r ON o.restaurant_id = r.id
WHERE r.id IS NULL;

🔍 Улика: у заказа #1006 restaurant_id = 9999, а имя ресторана NULL.

Шаг 6. Исправление архитектуры (Добавляем FOREIGN KEY)

Запрос, который разработчик обязан добавить в миграцию БД:

-- 1. Удаляем или исправляем битые заказы перед добавлением ключа
DELETE FROM orders WHERE restaurant_id = 9999;

-- 2. Вешаем внешний ключ (теперь база никогда не пропустит фейковый ресторан!)
ALTER TABLE orders 
ADD CONSTRAINT fk_orders_restaurant 
FOREIGN KEY (restaurant_id) REFERENCES restaurants(id);
